

# Phase 13 — Advanced Grouping

At this point, you know:

```csharp
.GroupBy(x => x.Key)
```

and you understand that it produces:

```csharp
IEnumerable<IGrouping<TKey, TElement>>
```

Now we go deeper.

Advanced grouping is mainly about:

- **composite keys**
    
- **custom equality**
    
- **grouping with projections**
    
- **group-level filtering**
    
- **nested grouping**
    
- **grouping + aggregation**
    
- **group ordering**
    
- **element ordering inside groups**
    
- **`ToLookup()`**
    
- **database translation considerations**
    

---

# 1. Composite Keys

A composite key means:

> Group by more than one property.

Suppose:

```csharp
class Sale
{
    public string Region { get; set; }
    public string Product { get; set; }
    public decimal Amount { get; set; }
}
```

You want:

> Group sales by both region and product.

Use:

```csharp
var groups = sales
    .GroupBy(s => new
    {
        s.Region,
        s.Product
    });
```

The key is now:

```text
{
    Region,
    Product
}
```

So instead of:

```text
Region
```

you have:

```text
Region + Product
```

---

# 2. Why anonymous types work well as grouping keys

Consider:

```csharp
.GroupBy(x => new
{
    x.Region,
    x.Product
});
```

Anonymous types have value-based equality semantics for their properties.

So:

```text
{ "South", "Laptop" }
```

and:

```text
{ "South", "Laptop" }
```

are treated as equal keys.

But:

```text
{ "South", "Laptop" }
```

and:

```text
{ "North", "Laptop" }
```

are different.

This makes anonymous types very convenient for composite grouping.

Suppose:

```text
Region     Product     Amount
--------------------------------
South      Laptop      50000
South      Laptop      30000
South      Phone       20000
North      Laptop      40000
North      Laptop      10000
```

Group:

```csharp
var result = sales
    .GroupBy(s => new
    {
        s.Region,
        s.Product
    });
```

Conceptually:

```text
South + Laptop
    50000
    30000

South + Phone
    20000

North + Laptop
    40000
    10000
```

# 4. Composite grouping + aggregation

Usually, grouping alone isn't the final goal.

You might want:

```csharp
var result = sales
    .GroupBy(s => new
    {
        s.Region,
        s.Product
    })
    .Select(g => new
    {
        Region = g.Key.Region,
        Product = g.Key.Product,
        TotalSales = g.Sum(s => s.Amount),
        SaleCount = g.Count()
    });
```

Result:

```text
South + Laptop
    Count = 2
    Total = 80000

South + Phone
    Count = 1
    Total = 20000

North + Laptop
    Count = 2
    Total = 50000
```

The important pattern is:

```text
GroupBy(composite key)
        ↓
g.Key.Region
g.Key.Product
        ↓
Aggregate
```

# 5. Grouping by a calculated key

Your grouping key doesn't have to be a property.

For example, categorize orders:

```csharp
var groups = orders
    .GroupBy(o =>
        o.Total >= 10000
            ? "Large"
            : "Small");
```

Now:

```text
Large
 ├── Order
 ├── Order
 └── Order

Small
 ├── Order
 └── Order
```

The key is generated by a function:

```text
Order → "Large" / "Small"
```

```csharp
var groups = people
```

Conceptually:


# 7. Grouping dates

Suppose:

```csharp
class Order
{
    public DateTime CreatedAt { get; set; }
    public decimal Total { get; set; }
}
```

You want sales by day:

```csharp
var dailySales = orders
    .GroupBy(o => o.CreatedAt.Date)
    .Select(g => new
    {
        Date = g.Key,
        Total = g.Sum(o => o.Total)
    });
```

Pipeline:

```text
Orders
   ↓
CreatedAt.Date
   ↓
Group by date
   ↓
Sum totals
```

Result:

```text
2026-08-28 → ₹120,000
2026-08-29 → ₹180,000
2026-08-30 → ₹150,000
```

# 8. Grouping by month

You can create a composite key:

```csharp
var monthlySales = orders
    .GroupBy(o => new
    {
        o.CreatedAt.Year,
        o.CreatedAt.Month
    })
    .Select(g => new
    {
        Year = g.Key.Year,
        Month = g.Key.Month,
        Total = g.Sum(o => o.Total)
    });
```

Why use both?

Because grouping only by:

```csharp
o.CreatedAt.Month
```

would combine:

```text
January 2025
January 2026
January 2027
```

into one group.

Using:

```csharp
new
{
    Year,
    Month
}
```

keeps them separate.

This is a classic example of why **composite keys matter**.

---

# 9. Grouping by year + month

The conceptual key is:

```text
(Year, Month)
```

So:

```text
2025 + January
2025 + February
...
2026 + January
2026 + February
```

rather than:

```text
January
February
...
```

This pattern is extremely common in reporting systems.

# 10. Filtering groups

After `GroupBy()`, `Where()` operates on **groups**.

Example:

> Find departments with at least 10 employees.

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Where(g => g.Count() >= 10);
```

The important type transition:

```text
IEnumerable<Employee>
        ↓
GroupBy
        ↓
IEnumerable<IGrouping<string, Employee>>
        ↓
Where
```

Therefore:

```csharp
g.Count()
```

counts employees **inside the group**.

---

# 11. Group filtering with multiple conditions

You can write:

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Where(g =>
        g.Count() >= 10 &&
        g.Average(e => e.Salary) > 80000);
```

Meaning:

> Keep departments containing at least 10 employees whose average salary exceeds ₹80,000.

The condition is evaluated **per group**.

---

# 12. `Where` before vs after `GroupBy`

This deserves special attention.

### Before grouping

```csharp
employees
    .Where(e => e.Salary > 80000)
    .GroupBy(e => e.Department);
```

Means:

> Only employees earning over ₹80k participate in grouping.

### After grouping

```csharp
employees
    .GroupBy(e => e.Department)
    .Where(g => g.Average(e => e.Salary) > 80000);
```

Means:

> Create all departments, then keep departments whose average salary exceeds ₹80k.

These are completely different queries.

---

# 13. `GroupBy` + `Select` can create a report

This is probably the most important advanced grouping pattern.

```csharp
var report = employees
    .GroupBy(e => e.Department)
    .Select(g => new
    {
        Department = g.Key,
        EmployeeCount = g.Count(),
        AverageSalary = g.Average(e => e.Salary),
        TotalSalary = g.Sum(e => e.Salary),
        HighestSalary = g.Max(e => e.Salary)
    });
```

Think:

```text
Employee records
      ↓
Group by Department
      ↓
One group per department
      ↓
Calculate statistics
      ↓
One report row per department
```

So the cardinality changes:

```text
Many employees
      ↓
Many groups
      ↓
One row per group
```

# 14. Ordering groups

Suppose:

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .OrderBy(g => g.Key);
```

You're ordering **groups** by their keys.

```text
Engineering
Finance
HR
Sales
```

Notice the lambda parameter:

```csharp
g => g.Key
```

`g` is a group.

Not an employee.

---

# 15. Ordering groups by aggregation

This is more interesting.

Suppose you want departments with the highest total salary first:

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .OrderByDescending(g => g.Sum(e => e.Salary));
```

The ordering key is calculated from each group:

```text
Engineering → Sum salaries
Sales       → Sum salaries
HR          → Sum salaries
                  ↓
             compare totals
```

You can then project:

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Select(g => new
    {
        Department = g.Key,
        TotalSalary = g.Sum(e => e.Salary)
    })
    .OrderByDescending(x => x.TotalSalary);
```

This version is often clearer because the aggregate is explicitly part of the result.

---

# 16. Ordering elements inside groups

Suppose you want:

> Every department, with employees sorted by salary descending.

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Select(g => new
    {
        Department = g.Key,
        Employees = g
            .OrderByDescending(e => e.Salary)
            .ToList()
    });
```

Now the structure is:

```text
Engineering
    Alice      ₹120k
    Charlie    ₹100k
    Bob         ₹90k

Sales
    David      ₹110k
    Eve         ₹80k
```

This is different from ordering the groups themselves.

```text
OrderBy(g => ...)
    → orders groups

g.OrderBy(e => ...)
    → orders elements inside a group
```

---

# 17. Nested grouping

You can group at multiple levels.

Suppose sales have:

```text
Region
Product
Amount
```

You can do:

```csharp
var result = sales
    .GroupBy(s => s.Region)
    .Select(regionGroup => new
    {
        Region = regionGroup.Key,

        Products = regionGroup
            .GroupBy(s => s.Product)
            .Select(productGroup => new
            {
                Product = productGroup.Key,
                Total = productGroup.Sum(s => s.Amount)
            })
    });
```

Conceptually:

```text
South
 ├── Laptop → ₹80k
 ├── Phone  → ₹20k
 └── Tablet → ₹15k

North
 ├── Laptop → ₹50k
 └── Phone  → ₹35k
```

This is useful when your output itself is hierarchical.

# 18. `SelectMany()` can flatten grouped results

Suppose you created:

```text
Region
   ↓
Products
```

You can flatten nested structures with:

```csharp
.SelectMany(...)
```

This connects directly to your earlier projection phase.

Remember:

```text
Select
→ preserves nesting

SelectMany
→ flattens nesting
```

For example:

```csharp
var employees = departments
    .GroupBy(...)
    .SelectMany(g => g);
```

can flatten groups back into a single employee sequence.

# 19. Grouping with custom equality

This becomes important when your key isn't naturally equal according to the default equality rules.

For example:

```csharp
var groups = names
    .GroupBy(
        name => name,
        StringComparer.OrdinalIgnoreCase);
```

Suppose:

```text
Alice
ALICE
alice
Bob
BOB
```

With case-insensitive comparison:

```text
Alice
 ├── Alice
 ├── ALICE
 └── alice

Bob
 ├── Bob
 └── BOB
```

The comparer determines which keys belong to the same group.

---

# 20. `IEqualityComparer<TKey>`

Conceptually, `GroupBy()` can accept:

```csharp
IEqualityComparer<TKey>
```

The comparer answers:

```text
Are these two keys equal?
```

and typically provides:

```text
GetHashCode(key)
```

This is important because grouping internally needs to efficiently associate elements with keys.

So grouping isn't just:

```text
compare everything with everything
```

It uses equality infrastructure.

---

# 21. Grouping and hash-based thinking

For LINQ-to-Objects, it's useful to mentally associate:

```text
GroupBy
   ↓
key
   ↓
equality + hashing
   ↓
groups
```

This is conceptually similar to how dictionaries work:

```text
Dictionary<TKey, TValue>
```

The exact implementation details are more nuanced, but the mental model is valuable.

It also explains why custom equality must have a consistent:

```text
Equals()
GetHashCode()
```

relationship.

# 22. Grouping and `ToLookup()`

`ToLookup()` is closely related to `GroupBy()`.

Example:

```csharp
var lookup = employees
    .ToLookup(e => e.Department);
```

Result:

```csharp
ILookup<string, Employee>
```

You can then do:

```csharp
var engineering = lookup["Engineering"];
```

Conceptually:

```text
Department → employees
```

This is an indexed grouping structure.

---

# 23. `GroupBy()` vs `ToLookup()`

A useful distinction:

### `GroupBy()`

```csharp
var groups = employees.GroupBy(e => e.Department);
```

Think:

> "Build a grouping as part of my query pipeline."

### `ToLookup()`

```csharp
var lookup = employees.ToLookup(e => e.Department);
```

Think:

> "Materialize an index that I will query by key."

So:

```text
GroupBy
→ query-oriented

ToLookup
→ lookup/index-oriented
```

`ToLookup()` is especially useful when you'll perform **multiple lookups by the same key**.

---

# 24. `ToLookup()` and missing keys

A useful difference from `Dictionary<TKey,TValue>`:

```csharp
var lookup = employees.ToLookup(e => e.Department);
```

Then:

```csharp
var result = lookup["DoesNotExist"];
```

returns an empty sequence rather than throwing a `KeyNotFoundException`.

Conceptually:

```text
Existing key
→ elements

Missing key
→ empty sequence
```

That's one reason `ILookup<TKey,TElement>` can be convenient for one-to-many relationships.

---

# 25. Grouping and materialization

You can materialize grouped results:

```csharp
var groups = employees
    .GroupBy(e => e.Department)
    .ToList();
```

Now you have a:

```text
List<IGrouping<string, Employee>>
```

Or create a dictionary:

```csharp
var dictionary = employees
    .GroupBy(e => e.Department)
    .ToDictionary(
        g => g.Key,
        g => g.ToList());
```

Result:

```text
Dictionary<string, List<Employee>>
```

This is useful when the consuming code actually needs dictionary semantics.

# 26. Grouping and database queries

This is where advanced grouping gets especially important.

With LINQ-to-Objects:

```csharp
employees
    .GroupBy(e => e.Department)
```

groups objects in memory.

With Entity Framework Core:

```csharp
db.Employees
    .GroupBy(e => e.Department)
```

the provider may translate a compatible query into SQL `GROUP BY`.

For example:

```csharp
var result = db.Employees
    .GroupBy(e => e.Department)
    .Select(g => new
    {
        Department = g.Key,
        Count = g.Count(),
        AverageSalary = g.Average(e => e.Salary)
    });
```

Conceptually becomes something like:

```sql
SELECT
    Department,
    COUNT(*),
    AVG(Salary)
FROM Employees
GROUP BY Department;
```

This is a major reason you should understand the difference between:

```text
IEnumerable<T>
```

and:

```text
IQueryable<T>
```

before doing serious database work.

---

# 27. Not every grouped LINQ expression translates to SQL

This is a critical production concern.

With LINQ-to-Objects, almost any valid C# grouping logic can potentially execute.

With a database provider, the provider must be able to **translate the expression**.

For example:

```csharp
.GroupBy(x => SomeComplexCSharpMethod(x))
```

may not translate cleanly to SQL.

So when working with:

```csharp
IQueryable<T>
```

always distinguish:

```text
Valid C# expression
```

from:

```text
Expression the query provider can translate
```

We'll study this deeply when we reach `IQueryable<T>` and expression trees.

---

# 28. Grouping and `null` keys

You may encounter:

```csharp
var groups = employees
    .GroupBy(e => e.Department);
```

where some employees have:

```csharp
Department = null;
```

LINQ-to-Objects can create a group corresponding to the null key.

The exact behavior and SQL translation can differ depending on the provider, so nullable grouping keys are another area where database semantics deserve attention.

# 29. Grouping by a normalized key

Suppose user input may have inconsistent casing or whitespace.

You can normalize:

```csharp
var groups = names
    .GroupBy(name => name.Trim().ToUpperInvariant());
```

Now:

```text
" Alice "
"alice"
"ALICE"
```

can map to the same normalized key:

```text
ALICE
```

But be careful: normalization rules are **business/data semantics**, not merely LINQ syntax.

For large datasets, especially database-backed queries, consider whether the normalization can be efficiently translated and whether it affects indexes.

# 30. Grouping and selecting the "best" element

Suppose:

> Get the highest-paid employee in each department.

A common LINQ approach is:

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Select(g => g
        .OrderByDescending(e => e.Salary)
        .First());
```

Pipeline:

```text
Employees
   ↓
GroupBy Department
   ↓
Each department
   ↓
Order employees by salary DESC
   ↓
First
   ↓
Highest-paid employee
```

This produces:

```text
Engineering → Employee
Sales       → Employee
HR          → Employee
```

---

# 31. `MaxBy()` makes that intent clearer

In modern .NET, you can often write:

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Select(g => g.MaxBy(e => e.Salary));
```

This directly expresses:

> From each group, select the element with the maximum salary.

Similarly:

```csharp
g.MinBy(e => e.Salary)
```

finds the minimum.

This is often cleaner than:

```csharp
g.OrderByDescending(e => e.Salary).First()
```

because you're looking for an extreme **element**, not trying to sort the whole group.

---

# 32. Grouping and `Max()` are not the same

Important distinction:

```csharp
g.Max(e => e.Salary)
```

returns:

```text
decimal
```

the maximum salary.

But:

```csharp
g.MaxBy(e => e.Salary)
```

returns:

```text
Employee
```

the employee who has that salary.

So:

```text
Max   → maximum value
MaxBy → element having maximum key
```

This is a useful extension of the aggregation concepts from Phase 10.

---

# 33. Grouping and `First()` have an ordering dependency

Consider:

```csharp
g.First()
```

This means:

> Give me the first element according to the group's current enumeration order.

It does **not** inherently mean:

> Give me the highest-paid employee.

For that:

```csharp
g.OrderByDescending(e => e.Salary).First()
```

or:

```csharp
g.MaxBy(e => e.Salary)
```

The distinction is important.

```csharp
var result = employees

```

Conceptually:

```text
Engineering
    ↓
Sort salary DESC
    ↓
Take 3

Sales
    ↓
Sort salary DESC
    ↓
Take 3

HR
    ↓
Sort salary DESC
    ↓

```

This is a very useful pattern in analytics.

# 35. Advanced pattern: group + filter + aggregate

Suppose:

> Find departments with at least 5 employees and average salary above ₹100,000.

```csharp
var result = employees
    .GroupBy(e => e.Department)
    .Where(g => g.Count() >= 5)
    .Select(g => new
    {
        Department = g.Key,
        AverageSalary = g.Average(e => e.Salary)
    })
    .Where(x => x.AverageSalary > 100000);
```

There are **two different levels of filtering**:

```text
Group-level:
Count >= 5

Result-level:
AverageSalary > 100000
```

This illustrates why understanding the current type flowing through the pipeline is essential.

# 36. SQL mental model

A useful conceptual translation is:

```text
LINQ                              SQL concept

Where(...)                    →   WHERE

GroupBy(key)                  →   GROUP BY

g.Count()                     →   COUNT

g.Sum(...)                    →   SUM

g.Average(...)                →   AVG

Where(g => g.Count() > 5)     →   HAVING-like condition

OrderBy(...)                  →   ORDER BY

Select(...)                   →   SELECT
```

For example:

```csharp
var result = employees
    .Where(e => e.Salary > 50000)
    .GroupBy(e => e.Department)
    .Where(g => g.Count() >= 5)
    .Select(g => new
    {
        Department = g.Key,
        AverageSalary = g.Average(e => e.Salary)
    });
```

Conceptually resembles:

```sql
SELECT
    Department,
    AVG(Salary)
FROM Employees
WHERE Salary > 50000
GROUP BY Department
HAVING COUNT(*) >= 5;
```

This isn't a universal one-to-one translation rule, but it's an excellent mental model.

# 37. The most important advanced grouping pattern

You will encounter this constantly:

```csharp
var result = source
    .Where(x => /* row filter */)
    .GroupBy(x => /* grouping key */)
    .Where(g => /* group filter */)
    .Select(g => new
    {
        Key = g.Key,
        Count = g.Count(),
        Total = g.Sum(x => /* value */),
        Average = g.Average(x => /* value */)
    })
    .OrderByDescending(x => x.Total);
```

Read it as:

```text
1. Filter individual records
2. Create groups
3. Filter groups
4. Calculate group statistics
5. Sort the resulting report
```

This is one of the most valuable LINQ patterns to internalize.

# 38. Type-flow: the advanced version

Suppose:

```csharp
var result = employees
    .Where(e => e.Salary > 50000)
    .GroupBy(e => e.Department)
    .Where(g => g.Count() >= 5)
    .Select(g => new
    {
        Department = g.Key,
        Total = g.Sum(e => e.Salary)
    });
```

Trace the types:

```text
IEnumerable<Employee>
        │
        ▼
Where
        │
        ▼
IEnumerable<Employee>
        │
        ▼
GroupBy
        │
        ▼
IEnumerable<IGrouping<string, Employee>>
        │
        ▼
Where
        │
        ▼
IEnumerable<IGrouping<string, Employee>>
        │
        ▼
Select
        │
        ▼
IEnumerable<AnonymousType>
```

Notice the crucial transition:

```text
Employee
   ↓
IGrouping<string, Employee>
```

After `GroupBy()`, your lambda variable changes meaning:

```csharp
.Where(e => ...)
```

→ `e` is an `Employee`.

But:

```csharp
.Where(g => ...)
```

after grouping

→ `g` is an `IGrouping`.

# Phase 13 — What you should now understand

### Basic grouping

```csharp
.GroupBy(x => x.Category)
```

→ partition elements by a key.

### Composite grouping

```csharp
.GroupBy(x => new { x.Year, x.Month })
```

→ group by multiple properties.

### Group filtering

```csharp
.GroupBy(...)
.Where(g => g.Count() > 5)
```

→ filter groups, not individual elements.

### Group aggregation

```csharp
.GroupBy(...)
.Select(g => new
{
    Key = g.Key,
    Total = g.Sum(...)
})
```

→ produce one result per group.

### Group ordering

```csharp
.OrderByDescending(g => g.Sum(...))
```

→ order the groups.

### Element ordering inside groups

```csharp
g.OrderByDescending(...)
```

→ order elements inside each group.

### Best element per group

```csharp
g.MaxBy(...)
```

→ retrieve the element with the maximum key.

### Composite time grouping

```csharp
.GroupBy(x => new { x.Year, x.Month })
```

→ avoid accidentally combining the same month across different years.

### Lookup

```csharp
.ToLookup(x => x.Key)
```

→ materialize a reusable one-to-many key index.

## The key principle

At this stage, don't think of `GroupBy()` as simply:

> "Put similar things together."

Think of it as a **type transformation**:

```text
IEnumerable<T>
      ↓
GroupBy(Func<T, TKey>)
      ↓
IEnumerable<IGrouping<TKey, T>>
```

Then each `IGrouping<TKey, T>` gives you:

```text
Key
 +
IEnumerable<T>
```

And from there you can perform another complete LINQ pipeline:

```text
Group
 ├── Where
 ├── Select
 ├── OrderBy
 ├── Take
 ├── Count
 ├── Sum
 ├── Average
 └── MaxBy
```

That is the real power of advanced grouping: **a group is itself an enumerable sequence**, so LINQ can recursively operate on the grouped data.
